יצירת צוות סוכנים — עקרונות, תבניות ותשתית

בפרק 8 פגשתם subagents — עוזרים שסוכן אחד מפעיל. עכשיו נעלה מדרגה: צוות סוכנים (Agent Squad) — קבוצת סוכנים עם תפקידים מוגדרים, חלוקת עבודה ותוצר משותף. כמו ההבדל בין עובד מוכשר אחד לבין מחלקה שלמה שעובדת בשבילכם.

מה נלמד בפרק

  • מתי סוכן אחד מפסיק להספיק — ומתי צוות הוא טעות
  • אנטומיה של צוות: תפקידים, מתאם, זיכרון משותף וחוזה תוצרים
  • שלוש תבניות ארגון: פס ייצור, מנהל־ועובדים, עבודה במקביל
  • בנייה בפועל: ב‑Claude Code וב‑Agent SDK

למה בכלל צוות?

לסוכן בודד, חזק ככל שיהיה, יש שלוש מגבלות מבניות:

  • חלון הקשר אחד. משימה גדולה באמת (מחקר + תכנון + ביצוע + בדיקה + תיעוד) מנפחת את ההקשר עד שהאיכות יורדת. פגשנו את זה בפרק 4.
  • כובע אחד בכל רגע. מי שכתב את הקוד מתקשה לבקר אותו באובייקטיביות — נכון לבני אדם, נכון גם לסוכנים. מבקר עם הנחיות נפרדות והקשר נקי מוצא בעיות שהכותב מפספס.
  • ריצה טורית. חמש משימות בלתי תלויות אצל סוכן אחד ירוצו בזו אחר זו. חמישה סוכנים יסיימו אותן בחמישית מהזמן.
⚠️ אבל אל תתלהבו מהר מדי צוות עולה יותר (טוקנים), מסובך יותר לתחזק, וקשה יותר לנפות בו תקלות. הכלל: מתחילים תמיד מסוכן אחד, ומפצלים לצוות רק כשנתקלים באחת משלוש המגבלות שלמעלה בפועל. צוות הוא פתרון לבעיה — לא קישוט.

אנטומיה של צוות סוכנים

כל צוות מוצלח, בכל תחום, בנוי מאותם ארבעה רכיבים:

רכיבמה זהאיך מממשים
מתאם (Orchestrator)מי שמפרק את המטרה למשימות, מאציל ומאחדהשיחה הראשית של Claude Code, או סקריפט SDK
מומחים (Specialists)סוכן לכל תפקיד: הנחיות, כלים והרשאות משלוקבצים ב‑.claude/agents/ (פרק 8)
זיכרון משותףהמקום שבו הצוות מחליף מידע ותוצריםקבצים בריפו: SPEC.md, PROGRESS.md, תיקיית artifacts/
חוזה תוצריםהגדרה מדויקת של מה כל תפקיד מקבל ומה הוא מחזירסעיף "קלט/פלט" ב‑system prompt של כל סוכן
💡 העיקרון החשוב מכולם: חוזה תוצרים צוותי סוכנים נכשלים כמעט תמיד באותה נקודה — סוכן א' מחזיר תוצר מעורפל, וסוכן ב' לא יודע מה לעשות איתו. הפתרון: כל סוכן מסיים בתוצר מוגדר — "קובץ PLAN.md עם רשימת צעדים ממוספרת", "דוח ממצאים בטבלה עם חומרה לכל שורה". תוצר מוגדר = מסירה נקייה.

שלוש תבניות ארגון

1. פס ייצור (Pipeline)

הסוכנים עובדים בזה אחר זה, כל אחד מקבל את תוצר קודמו: מתכנן ← מבצע ← בודק ← מתעד. פשוטה, צפויה, וקלה לניפוי תקלות — כשמשהו נשבר, ברור באיזו תחנה.

מתכנן ──► מבצע ──► בודק ──► מתעד
 SPEC.md   קוד     דוח      README

מתאימה כשיש סדר טבעי לעבודה, וכל שלב תלוי בקודמו.

2. מנהל ועובדים (Orchestrator–Workers)

סוכן מתאם מחזיק את התמונה הגדולה, מפרק את המשימה, ומאציל לכל מומחה את החלק שלו — לפי הצורך, לאו דווקא בסדר קבוע. המתאם מחליט בזמן אמת: "הממצא של החוקר מחייב עוד בדיקה? אשלח את הבודק שוב".

            ┌──► חוקר
  מתאם ──────┼──► מבצע
  (מחליט)    └──► מבקר
       ▲______________│ (תוצרים חוזרים אליו)

מתאימה כשהמשימה דורשת שיקול דעת על "מה עכשיו" — לא תסריט קבוע.

3. עבודה במקביל (Parallel–Merge)

מפצלים משימה לחלקים בלתי תלויים, כל סוכן עובד על חלק בו־זמנית, ובסוף שלב איחוד. הדרך הנקייה לעשות זאת בקוד: git worktrees — עותק עבודה נפרד לכל סוכן, כך שהם לא דורכים זה על זה:

macOS / Linux# עותק עבודה נפרד לכל סוכן, כל אחד על ענף משלו
git worktree add ../shop-payments feature/payments
git worktree add ../shop-search  feature/search

# טרמינל 1:
cd ../shop-payments && claude
# טרמינל 2:
cd ../shop-search && claude
Windows (PowerShell)git worktree add ..\shop-payments feature/payments
git worktree add ..\shop-search feature/search

# חלון טרמינל לכל סוכן:
cd ..\shop-payments; claude
cd ..\shop-search; claude

מתאימה כשיש חלקים שבאמת לא תלויים זה בזה. האיחוד (merge) הוא המקום שבו משלמים את המחיר — תכננו אותו מראש.

תבניתמתי לבחור בהנקודת התורפה
פס ייצורתהליך עם סדר ברור וקבועאיטית — הכול טורי
מנהל ועובדיםנדרש שיקול דעת דינמי על סדר העבודההמתאם הוא צוואר בקבוק ונקודת כשל
במקבילחלקים בלתי תלויים + לוח זמנים לחוץקונפליקטים בשלב האיחוד

בנייה בפועל, דרך 1: הכול בתוך Claude Code

הצוות מוגדר כקבוצת קבצים ב‑.claude/agents/ (בדיוק כמו בפרק 8), והשיחה הראשית משמשת מתאם. את תסריט העבודה אורזים בפקודה מותאמת — והצוות כולו מופעל במילה אחת:

.claude/commands/build-feature.mdאתה מתאם צוות. בנה את הפיצ'ר: $ARGUMENTS
תהליך העבודה, שלב אחר שלב:
1. שלח את planner לכתוב SPEC.md עם תוכנית מפורטת
2. הצג לי את התוכנית ועצור לאישור
3. אחרי אישור - שלח את coder לממש לפי ה-SPEC
4. שלח את test-writer לכסות את הקוד החדש בטסטים
5. שלח את code-reviewer לסקירה; ממצא קריטי חוזר ל-coder
6. סכם: מה נבנה, מה נבדק, ומה נשאר פתוח

שימו לב לשלב 2: עצירה לאישור אנושי בנקודת ההכרעה — עיקרון 5 מפרק 11, עכשיו ברמת הצוות.

בנייה בפועל, דרך 2: צוות בקוד עם ה‑Agent SDK

ב‑SDK מגדירים את חברי הצוות בתוך האפשרויות, והמודל מאציל להם בדיוק כמו ל‑subagents:

squad.tsimport { query } from "@anthropic-ai/claude-agent-sdk";

const result = query({
  prompt: "בנה עמוד 'צור קשר' מלא: תכנון, מימוש, טסטים וסקירה",
  options: {
    agents: {
      planner: {
        description: "מתכנן. הפעל ראשון לכל פיצ'ר חדש.",
        prompt: "כתוב תוכנית מימוש קצרה וממוספרת ל-SPEC.md. אל תכתוב קוד.",
        tools: ["Read", "Grep", "Glob", "Write"],
      },
      coder: {
        description: "מממש לפי SPEC.md קיים.",
        prompt: "ממש את הצעדים מ-SPEC.md אחד-אחד. עדכן PROGRESS.md אחרי כל צעד.",
      },
      reviewer: {
        description: "סוקר קוד. הפעל אחרי כל מימוש.",
        prompt: "סקור את ה-diff. החזר טבלת ממצאים עם חומרה. אל תערוך קבצים.",
        tools: ["Read", "Grep", "Bash"],
      },
    },
    maxTurns: 60,
  },
});

for await (const message of result) {
  if (message.type === "result") console.log(message.result);
}

אותם עקרונות בדיוק: תפקיד, חוזה תוצרים (SPEC.md,‏ PROGRESS.md, טבלת ממצאים), והרשאות לפי צורך — הסוקר לא מקבל Edit.

כללי אצבע לצוות בריא

  • 3–5 תפקידים לרוב מספיקים. צוות של עשרה סוכנים הוא כמעט תמיד סימן לפירוק לא נכון של הבעיה.
  • תפקיד אחד = אחריות אחת. אם קשה לכתוב לסוכן description במשפט, התפקיד רחב מדי.
  • מבקר אחד לפחות. צוות בלי תפקיד ביקורת (סוקר, בודק, עורך) הוא פס ייצור של טעויות מהירות.
  • הכול דרך הזיכרון המשותף. תוצר שלא נכתב לקובץ — לא קרה. זה מה שמאפשר לעצור, להמשיך מחר, ולנפות תקלות.

תרגילים

תרגיל 11.1 פס הייצור הראשון שלכם

צרו בפרויקט שלכם צוות מינימלי של שלושה: planner,‏ coder,‏ reviewer (אפשר להתבסס על הסוכנים מפרק 8). כתבו את הפקודה /build-feature מהדוגמה, והפעילו אותה על פיצ'ר קטן אמיתי. עקבו אחרי המסירות בין הסוכנים.

מה לבדוק

שלוש נקודות המסירה: SPEC.md נוצר ומפורט? הקוד באמת עוקב אחרי ה‑SPEC? דוח הסקירה מדורג ומצביע על קבצים? אם מסירה "דלפה" (סוכן התעלם מתוצר קודמו) — חדדו את חוזה התוצרים ב‑system prompt של המקבל: "קרא קודם את SPEC.md ופעל רק לפיו".

תרגיל 11.2 שני סוכנים במקביל

בחרו שתי משימות בלתי תלויות בפרויקט (למשל: שיפור עמוד א' ושיפור עמוד ב'). צרו שני worktrees, הריצו Claude בכל אחד במקביל, ובסוף מזגו את שני הענפים. תעדו: כמה זמן חסכתם, וכמה עלה לכם האיחוד?

לקח מרכזי

אם המיזוג עבר חלק — המשימות באמת היו בלתי תלויות, וזה הרווח האמיתי של התבנית. אם היו קונפליקטים — למדתם משהו חשוב יותר: הגבול בין המשימות עבר במקום הלא נכון. פיצול טוב הוא לאורך קווי התפר הטבעיים של הפרויקט (קבצים/תיקיות שונים), לא לרוחבם.

תרגיל 11.3 מהנדס הצוות

קחו את הצוות מתרגיל 11.1 ושברו אותו בכוונה: תנו ל‑planner לכתוב תוכנית מעורפלת בת שורה אחת ("תבנה את זה טוב"). הריצו את השרשרת וראו איך הטעות מתגלגלת במורד פס הייצור. אחר כך תקנו — הוסיפו ל‑planner דרישת מבנה (צעדים ממוספרים, קבצים מושפעים, קריטריון הצלחה) והריצו שוב.

למה התרגיל הזה חשוב

בצוות סוכנים, איכות התוצר נקבעת בחוליה החלשה — וכמעט תמיד זו איכות המסירה, לא איכות הסוכן. ההשוואה בין שתי הריצות מלמדת יותר מכל תיאוריה: תוכנית טובה בתחילת השרשרת שווה יותר מסוכן גאוני בסופה.

סיכום הפרק

  • צוות = תפקידים מוגדרים + מתאם + זיכרון משותף + חוזה תוצרים
  • שלוש תבניות: פס ייצור (סדר קבוע), מנהל־ועובדים (שיקול דעת), במקביל (מהירות)
  • מתחילים מסוכן אחד; מפצלים רק כשנתקלים במגבלה אמיתית
  • תוצר שלא נכתב לקובץ — לא קרה; מבקר אחד לפחות בכל צוות
