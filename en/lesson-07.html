MCP — connecting Claude to the world

Out of the install, Claude Code knows files and the terminal. But what about a real browser? A database? Your team's Slack? The MCP protocol is the "USB socket" that plugs new tools into Claude — and in this lesson we'll plug in a few.

What you'll learn

  • What MCP is and why it became a worldwide standard
  • Connecting a first MCP server: browser control
  • Connecting a database and external services
  • Configuration scopes and security considerations

The idea

MCP (Model Context Protocol) is an open protocol defining how an AI model talks to external tools. An MCP server is a small program exposing "tools" (e.g. open_page, run_query, send_message), and Claude — when connected to the server — sees those tools and can use them exactly like it uses file editing. Thousands of ready-made MCP servers exist today: GitHub, Slack, Postgres, Playwright, Figma, Notion, Stripe and more.

💡 Connecting to the big picture Remember the definition of an agent — "a model running tools in a loop"? MCP simply expands the toolbox. More tools = the agent can act on more of the world. An agent with a browser can check for itself the site it built. That's a fundamental shift.

First server: a browser with Playwright

Let's connect a server that gives Claude a real browser:

claude mcp add playwright -- npx @playwright/mcp@latest

That's it. Open Claude and try:

open the browser at http://localhost:3000, fill in the signup form
with sample data, submit, and screenshot the result. if something is broken - fix the code and check again

Re-read the end of that sentence: "if something is broken — fix and check again". Claude now has a full feedback loop on UI: it writes code, sees the result itself in the browser, and fixes. Exactly like a human developer.

Useful management commands:

claude mcp list          # which servers are connected and their status
claude mcp get playwright # server details
claude mcp remove playwright

Second server: a database

claude mcp add db -- npx -y @modelcontextprotocol/server-postgres "postgresql://readonly_user:pass@localhost:5432/shop"

Then in conversation:

how many orders were opened this month versus last month, broken down by city?
show a table and explain what stands out

Claude writes the SQL, runs it through the server, and interprets the results for you.

🛑 The golden rule: least privilege Notice we connected a readonly_user in the example. Never connect an agent to a real database with write permissions "because it's convenient". Same principle for any MCP server: install only servers from trusted sources, and give them the minimal permission that suffices for the task. A tool the agent doesn't need — don't connect.

Configuration scopes

ScopeWhere it's storedFor whom
local (default)Your personal settings for this projectYou only, this project only
projectA .mcp.json file at the repo rootThe whole team (goes into git)
userYour user settingsYou, in all projects
# a server the whole team gets automatically:
claude mcp add --scope project github -- npx -y @modelcontextprotocol/server-github

A .mcp.json in the repo is another brick of team infrastructure: whoever clones the project gets not only code, but every tool the agent needs to work on it.

Exercises

Exercise 7.1 A visual feedback loop

Connect the Playwright server. Open one of your course projects and ask: "open the page in the browser, screenshot it, and fix three styling issues you spot — after each fix screenshot again and verify it improved". Watch the loop work.

What should happen

Claude opens the page, screenshots, identifies issues (alignment, colors, text overflow), fixes the code and screenshots again to compare. If the page doesn't load — make sure you started a local server, or ask it to open the file directly (file://).

Exercise 7.2 Automated end-to-end checks

Continuing the previous exercise: ask Claude to write a full test scenario for your app (say, for the calculator: "press 7, +, 3, = and verify 10 is shown") and run it through the browser. Then break something on purpose and ask it to run again — verify the test catches the break.

Why it matters

Tests the agent can run itself are a necessary condition for autonomy: without them it has no way to know if it succeeded. "Break it and verify it's caught" proves the test is real, not always-green.

Exercise 7.3 A server of your choice

Pick one MCP server relevant to your work (GitHub? Notion? a side project's database?), connect it at the appropriate scope, and complete one real task with it. First ask Claude: "what tools do you get from this server?"

Tip

The question "what tools do you have now?" is a great way to understand any new server. And if something's off — claude mcp list shows whether the server even connected.

Lesson summary

  • MCP = a standard protocol adding tools to Claude: browser, DB, cloud services
  • Connecting is one command: claude mcp add name -- command
  • project scope + .mcp.json = shared tools for the whole team
  • Always least privilege: readonly when possible, trusted servers only
