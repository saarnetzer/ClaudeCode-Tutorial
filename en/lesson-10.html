Headless mode and CI automation

So far you've sat facing Claude. In this lesson you get up from the chair: we'll run it as a command in a script, plug it into GitHub Actions, and learn to tag @claude on a Pull Request — so it works even while you sleep. This is the first step to real autonomy.

What you'll learn

  • Headless mode: running Claude as a one-shot command
  • Controlling permissions and output format from the command line
  • Running safely with no approvals — in an isolated environment
  • GitHub Actions and tagging @claude

Headless mode: the ‎-p flag

The -p flag (or --print) runs Claude with no interactive interface: a question goes in, an answer comes out, the program exits:

claude -p "how many JS files are in the project and which is the largest?"

And once it's a regular command — you can chain it like any Unix tool:

# error-log analysis (macOS / Linux)
cat error.log | claude -p "what are the 3 most common errors and how to fix them?"

# the same analysis on Windows (PowerShell)
Get-Content error.log | claude -p "what are the 3 most common errors and how to fix them?"

# structured output for scripts (same on every OS)
claude -p "list all the TODOs in the code" --output-format json

With --output-format json you get JSON with the result, the run's cost and metadata — perfect for automated processing downstream.

Permissions with no human at the keyboard

In headless mode nobody clicks "approve". Three levels of control, from fine to coarse:

# 1. pre-approve specific tools only:
claude -p "run the tests and summarize failures" --allowedTools "Bash(npm test),Read"

# 2. cap the number of turns (a safety brake for any automated run):
claude -p "..." --max-turns 15

# 3. disable all approvals - only in an isolated environment!
claude -p "fix all the lint warnings" --dangerously-skip-permissions
🛑 The dangerous flag's rule --dangerously-skip-permissions is legitimate only when all three hold: (1) an isolated environment — a container or VM holding nothing beyond the project; (2) no access to real secrets; (3) the output passes review (a PR) before touching anything important. That's exactly how the CI environments we're about to see work — and how Anthropic's Claude Code on the web works, running every task in an isolated sandbox. You learned all the defense layers in Lesson 9.

GitHub Actions: an agent that responds to events

The fast way to connect Claude to your GitHub repo is from inside Claude Code:

/install-github-app

The install adds a workflow based on anthropics/claude-code-action. Once it's active, you can tag Claude on any issue or PR:

# replying to an issue:
@claude implement the feature described here and open a PR

# replying to a PR:
@claude there's a race-condition bug here, find and fix it

# automatic review:
@claude go over the changes and comment on security issues

Claude runs on GitHub's CI servers, performs the task, and pushes a branch or a comment — all without your machine.

Example: automatic review for every new PR

.github/workflows/claude-review.ymlname: Claude Auto Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Review this PR: possible bugs, security issues,
            and missing tests. Write the review as a PR comment,
            graded by severity.

Add your API key as a repo secret (ANTHROPIC_API_KEY) — and from now on every PR gets an automatic reviewer within minutes of opening.

✅ Everything you've built so far — works here too CLAUDE.md (Lesson 4), commands and Skills (Lesson 5), Hooks (Lesson 6), project MCP servers (Lesson 7) and subagents (Lesson 8) — all live in the repo, so the agent running in CI gets them automatically. Now it's clear why we invested in infrastructure: it's exactly what turns a remote agent from a "stranger" into a "teammate who knows the project".

A template for a local automation script

A useful pattern for periodic maintenance jobs:

nightly-deps.sh#!/bin/bash
set -e
git checkout -b chore/deps-$(date +%F)

claude -p "update the minor+patch dependencies only,
run the tests after every update, and revert any update that breaks them.
summarize in DEPS_REPORT.md what was updated and what was blocked and why" \
  --allowedTools "Bash(npm *),Edit,Read,Write" \
  --max-turns 40

git add -A && git commit -m "chore: nightly dependency updates"
git push -u origin HEAD
gh pr create --fill
nightly-deps.ps1 (Windows)$ErrorActionPreference = "Stop"
git checkout -b "chore/deps-$(Get-Date -Format 'yyyy-MM-dd')"

claude -p "update the minor+patch dependencies only,
run the tests after every update, and revert any update that breaks them.
summarize in DEPS_REPORT.md what was updated and what was blocked and why" `
  --allowedTools "Bash(npm *),Edit,Read,Write" `
  --max-turns 40

git add -A; git commit -m "chore: nightly dependency updates"
git push -u origin HEAD
gh pr create --fill

Note the principles: a separate branch, tools restricted to exactly the need, a turn cap, and the output is a PR — not a push to main. Automation with seatbelts.

Exercises

Exercise 10.1 First headless runs

Run three claude -p commands on one of your projects: one asking about the code, one piping a file in, and one with --output-format json. Look at the structure of the returned JSON.

What to look for in the JSON

Fields like result (the answer), the run's cost and the number of turns. In real automation it pays to monitor the cost field — that's how you keep a budget and spot runs that went wild.

Exercise 10.2 A maintenance script

Write a script (you can ask Claude to write it!) that runs with claude -p and performs a real maintenance task in your project: lint fixes, updating the README from the code, or adding JSDoc to public functions. Insist on a minimal --allowedTools and a --max-turns.

Checkpoint

Commit before the run; afterwards — git diff to review. If the script stops on a missing permission, add exactly the blocked tool to allowedTools — not everything. That's how you build least-privilege automation, iteratively.

Exercise 10.3 @claude on a real repo

Required: a GitHub account and a repo of your own (setup guide if you don't have one yet). In your repo, run /install-github-app and complete the setup. Open an issue describing a small, precise feature, and tag: @claude implement this and open a PR. Review the resulting PR — critically, as if a new team member wrote it.

What should happen

Within minutes you'll see Claude respond on the issue with a progress checklist, and at the end — a link to a ready PR. If the result isn't perfect, continue the dialogue in the PR's comments: @claude the button should work on mobile too. That's a full handoff to asynchronous work.
