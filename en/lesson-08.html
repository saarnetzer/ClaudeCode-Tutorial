Subagents — a team of specialists

Why one agent when you can have a team? Subagents are specialist agents — a code reviewer, a test writer, a researcher — that the main agent activates by itself when a task fits them. Each with its own instructions, its own tools, and its own clean context window.

What you'll learn

  • What a subagent is and why a separate context is a huge advantage
  • Creating a first subagent: a code reviewer
  • Restricting tools per agent — permissions by role
  • When subagents help and when they're overhead

The idea

A subagent is a "worker" the main agent can delegate a task to. Three properties make it powerful:

  • A separate context. The subagent works in its own clean context window. It can read fifty files and return only the bottom line to the main agent — and the main conversation's context stays clean. That solves the "conversation bloat" problem from Lesson 4.
  • Specialization. Every subagent has its own system prompt: detailed instructions for one role, no noise.
  • Its own permissions. You decide which tools it may use — a code reviewer, for instance, gets read-only.

A subagent is defined as a Markdown file in .claude/agents/ (per project) or ~/.claude/agents/ (personal). You can also manage them with the interactive /agents command.

First subagent: a code reviewer

.claude/agents/code-reviewer.md---
name: code-reviewer
description: A strict code reviewer. Use proactively after any
  significant code change, and before every commit.
tools: Read, Grep, Glob, Bash
---

You are a senior code reviewer. When you get a task:
1. Run git diff to see what changed
2. Go over every changed file and check:
   - logic bugs and unhandled edge cases
   - security issues (unsanitized input, secrets in code, permissions)
   - duplicated code or unnecessary complexity
   - consistency with the project's existing style
3. Rate every finding: critical / should fix / cosmetic

Return an orderly report citing file and line for each finding.
Do not edit files - you review, you don't fix.

Note three things:

  • The description explicitly says when to activate — including the word "proactively", which encourages the main agent to call it without being asked.
  • The tools line gives it read and search only (plus Bash for git diff) — no Edit or Write. The instruction "don't edit" is backed by permissions. That's the Hooks principle from Lesson 6 again: not promises, mechanisms.
  • The file body is its full system prompt — a detailed, step-by-step working process.

After saving the file, you can invoke it explicitly ("have code-reviewer go over the changes") — or just work normally and watch the main agent call it on its own after big changes.

Two more workers for the team

.claude/agents/test-writer.md---
name: test-writer
description: Writes tests. Use when new or existing code needs test coverage.
---

You are a test-writing expert. Identify the framework already used in
the project and use it. For every function write: the happy path,
edge cases, and failure cases.
Run the tests and make sure they pass before you finish.
A test failing on existing code = an important finding; report it, don't hide it.
.claude/agents/researcher.md---
name: researcher
description: A read-only code researcher. Use for "how does X work" or
  "where is Y" questions in large projects, to save context in the main conversation.
tools: Read, Grep, Glob
---

You are a code researcher. Answer the question you were given concisely:
the mechanism, the key files (with paths), and the data flow.
Return a short, focused answer - not everything you read.

The researcher demonstrates the "clean context" pattern at its best: it reads a lot and returns a little. In large projects this saves thousands of tokens in the main conversation.

⚠️ When not to use one A subagent starts every task "cold" — without the conversation history — and talking to it costs time and tokens. For small tasks in a flowing conversation it's needless overhead. The rule: an independent, large, or specialization-demanding task — subagent; flowing dialogue — the main agent.

Exercises

Exercise 8.1 Assemble the team

Create code-reviewer in your project (copy the example and adapt it to your rules). Make a code change with a small deliberate bug (e.g. an inverted condition), and ask for a review. Verify the bug is caught and you get a graded report.

What should happen

You'll see in the interface that the task is handed to a subagent (separate indicator), and the report comes back structured per the instructions. If the reviewer "misses" the bug — sharpen its system prompt. Writing instructions for an agent is a skill you train.

Exercise 8.2 A work chain

Create test-writer too, then give the main agent a combined task: "add a quantity-based discount function, have test-writer cover it with tests, then have code-reviewer review everything". Watch the team management.

What to look for

The main agent acts as a manager: writes the code, delegates the tests, delegates the review, and merges the results. If the review raises a critical finding — ask it to fix and re-review. You've got a full quality pipeline in one command.

Exercise 8.3 An agent of your own

Think of a specialization you are missing — an API documenter? accessibility checker? UI translator? — and write it a complete subagent: a description that gets it called at the right time, tools matching the real need, and a detailed process. Run it on a real task.

Sample idea

a11y-checker: Read/Grep/Glob tools only; checks image alts, color contrast, form labels, keyboard navigation; returns a report with severity and a suggested fix per finding. Pairs beautifully with Playwright from Lesson 7.

Self-check

2. How do you make sure the code reviewer really can't edit files?

3. When is a subagent needless overhead?

Lesson summary

  • A subagent = a specialist agent with its own instructions, tools and context
  • Defined as Markdown in .claude/agents/; the description decides when it gets called
  • Permissions by role: the reviewer doesn't write, the researcher doesn't edit
  • Separate context = reads a lot, returns a little — the main conversation stays clean
