Working with Git and GitHub

Git is the safety net that turns working with an agent from scary to calm: every change is recorded, and every mistake is reversible. The good news — with Claude Code you don't need to memorize a single git command. Ask in words; it executes.

What you'll learn

  • Why Git matters especially when working with AI agents
  • Commits and branches in plain language
  • Creating a Pull Request from the terminal
  • Recovering from mistakes — your strongest card

Why Git + agent = a winning pair

When an agent edits dozens of files for you, two questions become critical: "what exactly did it change?" and "how do I undo it if it's bad?". Git answers both. Hence the rule: before any significant task — commit. After every step that worked — commit. Small, frequent commits are the seatbelt of working with AI.

💡 New to Git? Totally fine. Think of Git as "save points in a game": commit = save. You can always return to a previous save. A branch = starting an alternate storyline you can merge back or discard. With Claude Code you don't need to know more than that to begin.

Git not installed yet? No GitHub account? We have a step-by-step setup guide: what Git and GitHub are, installing on any OS, opening an account and connecting your machine — fifteen minutes and you're set.

Everything in plain language

Instead of remembering syntax, just ask:

what changed in the project since the last commit? show me a summary before we save
commit the changes with an appropriate message
open a new branch named feature/dark-mode and switch to it
who last changed this function and why? check the history

Claude runs the right git commands (you'll see and approve them), writes quality commit messages based on the actual change, and even knows how to dig through history to answer "detective" questions.

A real scenario: a full feature on a branch

1. open a branch feature/contact-form
2. add a contact form to the main page with validation
3. run the tests
4. if everything is green - commit with a tidy message

Notice: we gave a whole sequence of steps in one request. Claude performs them in order, stopping for your approval at the sensitive points. That's already "agentic" thinking — you define a process, not commands.

Pull Requests

If you have the GitHub CLI installed (the gh command) and you're signed in, Claude can open a PR for you:

push the branch and open a Pull Request. in the description explain what changed, why, and how we tested

Claude will go over the branch changes, write a title and description that genuinely summarize them (not just "update code"), and hand you a link to the finished PR.

✅ PR review, too It works in the other direction as well: look at PR number 42 and give me a review — possible bugs, security issues, improvement suggestions. You get a dedicated code reviewer, available 24/7.

Recovering from mistakes

Something bad happened? First — touch nothing, ask:

I made a mess. show me the current git state and my options, without changing anything

Then, as needed:

discard all uncommitted changes and return to the last clean state
the last commit was a mistake - undo it but keep the changes in the files
⚠️ Destructive operations For destructive actions (discarding changes, hard reset) Claude will always ask for explicit approval and explain what will be deleted. Read the explanation before approving — this is exactly where the "normal" permission mode is worth gold.

Exercises

Exercise 3.1 A first managed repo

Take one of the projects from previous lessons and ask Claude to: initialize a git repo, create a suitable .gitignore, and make a first commit. Then change something small and ask "show me what changed and commit".

What should happen

Claude will run git init, figure out which files don't belong in the repo (node_modules, temp files) for the gitignore, and write a commit message describing the content. Notice the second message describes the change, not the project.

Exercise 3.2 Practicing recovery — on purpose

In the previous exercise's project (after a commit!), ask Claude to "delete half the code in the main file" (yes, really). Then recover: "return to the state of the last commit". Verify everything came back.

Why this exercise matters

Whoever experiences one successful recovery stops being afraid. The fear "the agent will ruin something" evaporates when you know for certain that anything after a commit is reversible in 10 seconds. It changes your entire way of working.

Exercise 3.3 A feature end to end

Create a repo on GitHub (or use an existing one), and run the full flow in one request: new branch → a real change → commit → push → Pull Request with a full description. Required: a GitHub account (free — setup guide) and gh installed and signed in (gh auth login).

Peek at the solution

Sample request: open a branch fix/typos, fix typos in the README, commit, push, and open a PR with a description. If gh isn't signed in, Claude will tell you and explain how — that's a way to learn, too.
