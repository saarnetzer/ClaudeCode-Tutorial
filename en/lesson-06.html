Hooks — automating your workflow

Until now we asked Claude to do things. Hooks are the opposite: your code running automatically around Claude's actions — no asking, no relying on memory, one hundred percent of the time. It's the difference between "please run the formatter" and "the formatter always runs, period".

What you'll learn

  • What a Hook is and which events you can attach to
  • A first hook: auto-format after every edit
  • Hooks as gatekeepers: blocking dangerous actions
  • Why hooks are critical for autonomous agents

The idea

A Hook is a system command defined in Claude Code's settings file that runs automatically when a certain event occurs. The main events:

EventWhen it runsTypical use
PreToolUseBefore a tool runs (edit, command...)Blocking forbidden actions
PostToolUseAfter a tool ran successfullyFormat, lint, automatic checks
UserPromptSubmitWhen you send a messageInjecting context, validating requests
StopWhen Claude finishes respondingNotification, "are you really done?" checks
NotificationWhen Claude waits for approvalSound/message when you're needed

The settings live in .claude/settings.json (per project, shared with the team) or ~/.claude/settings.json (personal). The convenient way to start: the /hooks command inside Claude Code, which walks you through interactively.

Example 1: auto-format after every edit

.claude/settings.json{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write \"$CLAUDE_FILE_PATHS\" 2>/dev/null || true"
          }
        ]
      }
    ]
  }
}

What happens here: every time Claude edits or writes a file (the matcher catches the Edit and Write tools), prettier runs on the touched file. From now on there is no "forgot to format" — there is a law of nature.

💡 Why not just write it in CLAUDE.md? Because an instruction in memory is a request — the model will almost always honor it, but "almost always" isn't "always". A Hook is a mechanism — it runs regardless. Rule of thumb: preferences → CLAUDE.md; rules that must never break → Hooks.

Example 2: a gatekeeper that blocks dangerous actions

A PreToolUse hook receives the planned action's details on stdin (JSON), and can block it: exiting with code 2 tells Claude "forbidden, and here's why" (whatever was written to stderr goes back to it as the explanation).

.claude/hooks/guard.py#!/usr/bin/env python3
import json, sys, re

data = json.load(sys.stdin)
if data.get("tool_name") == "Bash":
    cmd = data.get("tool_input", {}).get("command", "")
    banned = [r"rm\s+-rf\s+[/~]", r"git\s+push\s+--force", r"DROP\s+TABLE"]
    for pattern in banned:
        if re.search(pattern, cmd, re.IGNORECASE):
            print(f"Blocked dangerous command: {cmd}", file=sys.stderr)
            sys.exit(2)   # exit 2 = block + explain to Claude
sys.exit(0)
.claude/settings.json (fragment){
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "python3 .claude/hooks/guard.py" }
        ]
      }
    ]
  }
}

Now even if Claude tries (or is convinced by a confused request of yours...) to run rm -rf / — the action is blocked at the system level, and it gets an explanation and finds another way.

Example 3: a notification when you're needed

Gave Claude a long task and went for coffee? Have it announce when it needs approval:

.claude/settings.json (fragment, macOS){
  "hooks": {
    "Notification": [
      {
        "hooks": [
          { "type": "command", "command": "afplay /System/Library/Sounds/Glass.aiff" }
        ]
      }
    ]
  }
}
.claude/settings.json (fragment, Windows){
  "hooks": {
    "Notification": [
      {
        "hooks": [
          { "type": "command", "command": "powershell -c [console]::beep(800,300)" }
        ]
      }
    ]
  }
}

And on Linux: notify-send "Claude is waiting for you".

Why this is a gateway to autonomy

Think about what we've built: a system where the agent has freedom of action, but boundaries enforced in code, not promises. Formatting and quality enforced automatically (PostToolUse), destructive actions physically blocked (PreToolUse), and humans notified at decision points (Notification). This is exactly the infrastructure that will let us, in Lessons 10–11, let go of the wheel with confidence: the harder the boundaries — the more freedom the agent can have inside them.

Exercises

Exercise 6.1 A first hook

Define a PostToolUse hook that runs after every file edit and appends a log line to .claude/edits.log (date + path). Ask Claude to edit something, and verify the log updates. Tip: you can ask Claude itself to write the config!

Sample solution 
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "echo \"$(date '+%F %T') $CLAUDE_FILE_PATHS\" >> .claude/edits.log"
          }
        ]
      }
    ]
  }
}

On Windows replace the command with: powershell -c "Add-Content .claude/edits.log \"$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss') $env:CLAUDE_FILE_PATHS\""

A log like this is an excellent way to "see" what an agent did during long runs.

Exercise 6.2 Your own gatekeeper

Write a PreToolUse hook (you can build on the Python above) that blocks any edit of files under a secrets/ folder. Create such a folder with a dummy file, explicitly ask Claude to edit it — and verify it gets blocked and explains why.

Solution direction

In the matcher catch Edit|Write. In the script check whether tool_input.file_path contains secrets/ — if so, exit 2 with an explanation on stderr. The important experience: seeing Claude accept the block, explain it to you, and not try to work around it.

Exercise 6.3 "Are you really done?"

Define a Stop hook that runs the project's tests when Claude finishes responding, and writes the result to a file. Upgrade: think (and check the /hooks docs) how a Stop hook can send Claude back to work when tests fail.

Solution direction

A Stop hook that exits with code 2 and explains on stderr ("tests failed, fix before finishing") sends Claude back to work. Beware infinite loops — bound the check so it can't fail forever. This pattern, "you're not done until the checks are green", is one of the strongest autonomy engines.

Self-check

1. Why is a Hook better than a CLAUDE.md instruction for unbreakable rules?

2. How does a PreToolUse hook block an action and explain why?

3. You want the formatter to run automatically after every file edit. Which event?

Lesson summary

  • Hooks = your code running automatically around Claude's actions
  • PostToolUse to enforce quality, PreToolUse to block dangers, Notification for alerts
  • exit code 2 + stderr = a block with an explanation that goes back to Claude
  • Preferences → CLAUDE.md; absolute rules → Hooks
