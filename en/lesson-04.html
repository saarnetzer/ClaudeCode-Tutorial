Memory and context: CLAUDE.md and context management

The difference between "Claude that works okay" and "Claude that feels like a veteran teammate" is almost always one small file: CLAUDE.md. In this lesson we'll teach Claude our project once — and keep conversations sharp and focused.

What you'll learn

  • What the context window is and why it's your scarcest resource
  • The CLAUDE.md file: what goes in and what doesn't
  • Three memory levels: project, personal, and global
  • Techniques for managing long conversations
  • Choosing a model and an effort level — quality, time and cost

First, a concept: the context window

Every conversation with Claude has limited "working memory" — the context window. Everything said, every file read and every command output takes up room in it. When it fills up, older details get compressed or forgotten. Two practical rules follow:

  • A new conversation for every new task. Finished a feature? /clear. There's no reason to drag thousands of lines of stale, distracting context into a new task.
  • Whatever always matters — belongs in a file, not the conversation. That is exactly CLAUDE.md's job.

CLAUDE.md — the project's ID card

At the start of every conversation, Claude automatically reads the CLAUDE.md file in the project folder. Whatever is written there — it simply knows, without you repeating it. To generate a first draft automatically:

/init

Claude scans the project and writes a starter file. But the real value comes from your editing. A recommended structure:

CLAUDE.md# MyShop — online store

## Commands
- Local dev: `npm run dev`
- Tests: `npm test` (required before every commit)
- Lint: `npm run lint`

## Architecture
- Frontend: React + Vite in `client/`
- Backend: Express in `server/`, routes in `server/routes/`
- DB: PostgreSQL via Prisma. Schema in `prisma/schema.prisma`

## Important rules
- All user-facing text in Hebrew. Variable names in English
- Never touch `legacy/` without explicit approval
- Dates always UTC on the server, convert to local time only for display
- After any schema change run `npx prisma generate`
✅ The CLAUDE.md quality test Ask yourself: "if a new developer joined tomorrow, what would I have to tell them on day one?" — that's exactly what belongs in the file. Short, factual, no rambling. A huge file hurts more than it helps, because it loads into every conversation.

Updating as you work

Caught yourself explaining something to Claude for the second time? That's a sign it belongs in memory. Start a message with a hash # — and Claude will offer to add it to the memory file:

# always use axios, not fetch, in this project

Three memory levels

FileScopeWhen
./CLAUDE.mdThe project — shared with the team (in git)Commands, architecture, team rules
./CLAUDE.local.mdThe project — you only (outside git)Local paths, personal per-project preferences
~/.claude/CLAUDE.mdEvery project on your machine"answer in Hebrew", personal code style
💡 Where's that on Windows? The ~ symbol means your home folder. On Windows that's C:\Users\<username> — so ~/.claude/CLAUDE.md is C:\Users\<username>\.claude\CLAUDE.md.

In a large project you can also put CLAUDE.md files in subfolders — Claude loads them when working in the relevant area. And you can split things up: a line of the form @path/to/file.md inside CLAUDE.md imports another file into it.

When the file bloats: the .claude/rules/ directory

A single CLAUDE.md trying to cover everything becomes a wall of text nobody maintains. The answer is to split it by topic: every .md file inside .claude/rules/ loads as part of the project's instructions. The directory is scanned recursively, so you can organize into subdirectories:

.claude/rules/
├── testing.md
├── frontend/
│   └── rtl.md
└── backend/
    └── api.md

And here's the interesting part: a rule can be tied to specific files only, with a paths field in its frontmatter:

.claude/rules/frontend/rtl.md---
paths:
  - "src/components/**/*.tsx"
---

In every UI component: dir="rtl" on the root element,
margin-inline-start instead of margin-left,
and numbers and code stay LTR.

A rule with paths loads only when Claude touches a file matching the pattern. A rule without it loads at the start of the session, exactly like CLAUDE.md. That keeps the context lean: your RTL rules take up no room while you're working on the backend.

There's also ~/.claude/rules/ for your personal rules across every project.

AGENTS.md — the shared standard

Other tools on the market use a file called AGENTS.md for the same purpose. Claude reads it — but only if there is no CLAUDE.md in the working directory or above it. So if you're coming from another tool, your existing file simply works; and if you add a CLAUDE.md, that one wins.

Auto memory — what Claude writes by itself

So far we've dealt with the memory you write. But there's a second layer, and it's on by default: Claude keeps its own notes about your preferences and the corrections you've given it, and loads them in later sessions. That's why it remembers things you never wrote in any file.

Four kinds of note are saved:

TypeWhat it holds
userYour role, your areas of expertise and how you prefer to work
feedbackCorrections you gave, and approaches you confirmed
projectOngoing work, deadlines and decisions that can't be derived from the code or the history
referenceWhere information lives outside the project — an issue tracker, a dashboard

The /memory command is where you see what's been saved, and turn it off if you'd rather. The notes load from an index file called MEMORY.md — Claude reads its first 200 lines (or 25KB) at the start of every session.

⚠️ Worth knowing this exists It's genuinely convenient — and it also means information is being collected about you that you never wrote down explicitly. To turn it off entirely on your machine: open /memory and use the toggle. To turn it off for one project only, in that project's settings: 
.claude/settings.json{
  "autoMemoryEnabled": false
}
💡 Memory is not enforcement A distinction that returns in Lesson 9: both CLAUDE.md and auto memory are context, not enforced configuration. They shape what Claude knows and tends to do — but a rule that must be enforced belongs in permissions or a hook, not in a memory file.

Managing long conversations

  • /compact — compresses history into a summary. Use at a natural stopping point (after a commit, before a new subtask).
  • /clear — full reset. Better than compact when switching to an unrelated task.
  • /context — shows exactly what is sitting in the context window right now, as a coloured map: how much the memory file takes, how much the tool results take, and how much room is left. This is how you stop guessing when to run /compact.
  • /btw — a side question about the session ("hang on, what is this file?") that never enters the history. Exactly right for curiosity that shouldn't cost you context.
  • /add-dir path — add another working directory mid-session, when it turns out the task touches the neighbouring repo too.
  • Deliberate interim summaries: before a long break ask "summarize into PROGRESS.md what we did, what works and what's left" — and open the next conversation with "read PROGRESS.md and let's continue".
💡 The organizing principle Context is a precious resource: every wasted token reduces focus. Agents work best when the context holds exactly what's relevant — no less, and no more. Think of yourselves as the agent's context managers.

Model and effort — the lever that saves you most

Context isn't the only resource you manage. There are two more levers, both of which directly affect quality, time and cost — and most people never touch them.

Which model

The /model command switches models. You don't need to remember version names — there are aliases that always point at the current one:

AliasWhat it's for
haikuFast and cheap — for simple tasks
sonnetDay-to-day coding. A sensible starting point for most things
opusTasks that need complex reasoning
opusplanA neat hybrid: opus while planning, then sonnet to execute
fableThe hardest, longest problems — root-cause investigation, outage debugging, architecture decisions
defaultClear your choice and go back to your account's default

opusplan deserves particular attention: it puts the stronger reasoning exactly where it matters most — the planning — and the efficient model on the writing itself. That's the Plan Mode workflow from Lesson 2, automated.

How much effort

The same model can work shallow or deep. That's the effort level, switched with /effort:

/effort low      # short exchanges you review yourself: a rename, brainstorming
/effort medium   # the default on current models. Day-to-day work with clear scope
/effort high     # when verification matters or edge cases are likely — a bug in existing code
/effort xhigh    # deeper reasoning, at higher cost
/effort max      # hard problems the agent should crack unattended, e.g. hunting vulnerabilities
/effort status   # what the level is right now
⚠️ More effort is not always better The documentation itself warns that max shows diminishing returns and is prone to overthinking, and that you should test before adopting it broadly. The practical rule: start at medium, and raise it only once you've seen the result fall short — not "just to be safe".

The word that actually works — and two that don't

There's a common myth that writing "think hard" or "think more" in a prompt triggers something. It doesn't. Those phrases pass through as ordinary text. What does work is one specific word: ultrathink. If it appears in your prompt, it requests deeper reasoning for that turn only, without changing the session's effort level:

ultrathink — why does this test fail only in CI and not on my machine?

Seeing where the money goes

And if you'd like to see patterns over time — /insights generates an HTML report on your recent sessions on this machine: which projects you work in, how you use the tool, and where things get stuck.

And finally, measurement: /usage (also /cost) shows what the session cost and where you stand against your plan limits. Worth a look after a big task — it's how you build intuition for what's expensive and what isn't.

Exercises

Exercise 4.1 A first CLAUDE.md

In a project you worked on in previous lessons, run /init. Read the generated file, delete anything unnecessary, and add two personal rules of your own (e.g. "user-facing text in Hebrew"). Open a new conversation and check the rules really apply.

How to verify it works

After /clear, ask for something the rule should affect — e.g. "add a new button" — and check the text comes out in the right language without asking. If so: memory works.

Exercise 4.2 Global memory

Create ~/.claude/CLAUDE.md with 2–3 preferences that are always true for you (language, answer style, favorite tools). Open Claude in two different folders and verify the preferences apply in both.

Sample content 
# Personal preferences
- answer me in Hebrew, code in English
- before a big change - show a short plan
- prefer a simple solution over a "clever" one
Exercise 4.3 Passing the baton between conversations

Start a multi-step task (e.g.: an "About" page + navigation + styling). Midway, ask Claude to write a progress summary to PROGRESS.md. Run /clear, then: "read PROGRESS.md and continue where we stopped". Verify it truly picks up correctly.

Why this matters

This technique — keeping state in files instead of conversation memory — is a cornerstone of autonomous agents (Lesson 11). An agent that runs for hours needs "external memory" that survives context resets. You're already practicing it by hand.

Self-check

1. What happens with CLAUDE.md at the start of every conversation?

2. You finished a feature and are moving to something unrelated. What's right?

3. How do you add a rule to memory mid-conversation?

Lesson summary

  • The context window is limited — manage it deliberately: /clear between tasks, /compact at stopping points, /context to see what's inside
  • CLAUDE.md = what you'd tell a new developer on day one
  • Three levels: project (shared), local (personal per project), global (~/.claude)
  • Important knowledge lives in files — not conversation memory
  • /model and /effort are the most practical levers — start at sonnet and medium, raise only when needed
