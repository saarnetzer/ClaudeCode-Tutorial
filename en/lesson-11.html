Fully autonomous agents — the Agent SDK and working principles

In this lesson we build our own agent in code with the Claude Agent SDK — the same engine that powers Claude Code itself — and learn the five principles that separate an autonomous agent that creates value from one that creates chaos.

What you'll learn

  • What the Claude Agent SDK is and why it's the best starting point
  • A first agent in TypeScript and Python
  • Adding custom tools and programmatic permissions
  • The five principles of safe autonomy
  • Where to go next

What is the Agent SDK

The Claude Agent SDK is a library (TypeScript and Python) that gives you, in code, everything that drives Claude Code: the agentic loop (think → tool → result → think...), the file and terminal tools, the permission system, subagents, hooks and MCP. Instead of building agent infrastructure from scratch — you get the proven infrastructure and assemble your agent on top: the logic, the boundaries, and the integration into your system.

# TypeScript
npm install @anthropic-ai/claude-agent-sdk

# Python
pip install claude-agent-sdk

A first agent: 20 lines

TypeScript

agent.tsimport { query } from "@anthropic-ai/claude-agent-sdk";

const result = query({
  prompt: "find all the TODOs in the project and summarize them into TODO_REPORT.md",
  options: {
    cwd: "/path/to/project",
    allowedTools: ["Read", "Grep", "Glob", "Write"],
    maxTurns: 20,
  },
});

for await (const message of result) {
  if (message.type === "assistant") {
    console.log(message.message.content);   // watch the agent "think"
  }
  if (message.type === "result") {
    console.log("Summary:", message.result);
    console.log("Cost ($):", message.total_cost_usd);
  }
}

Python

agent.pyimport anyio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    async for message in query(
        prompt="find all the TODOs in the project and summarize them into TODO_REPORT.md",
        options=ClaudeAgentOptions(
            cwd="/path/to/project",
            allowed_tools=["Read", "Grep", "Glob", "Write"],
            max_turns=20,
        ),
    ):
        print(message)

anyio.run(main)

Run it — and watch the agent work in the output: searching, reading, writing, returning a final result with a cost. This is a real autonomous agent: you gave a goal, and it chose the steps itself.

A custom tool

The real power: giving the agent tools from your world. Custom tools are defined as an in-process MCP server:

tools.tsimport { tool, createSdkMcpServer, query } from "@anthropic-ai/claude-agent-sdk";
import { z } from "zod";

const sendAlert = tool(
  "send_alert",
  "Sends an alert to the ops team. Use only for high-severity incidents.",
  { message: z.string(), severity: z.enum(["low", "high"]) },
  async (args) => {
    await notifyOps(args.message, args.severity);   // your logic
    return { content: [{ type: "text", text: "Alert sent" }] };
  }
);

const opsServer = createSdkMcpServer({
  name: "ops-tools",
  tools: [sendAlert],
});

const result = query({
  prompt: "check last night's logs. if there's a severe incident - send an alert",
  options: {
    mcpServers: { "ops-tools": opsServer },
    allowedTools: ["Read", "Grep", "mcp__ops-tools__send_alert"],
    maxTurns: 30,
  },
});

Note the tool's description — "use only for severe incidents". As with Skills and subagents, the description is the interface between your intent and the agent's judgment. Want harder control? The SDK also supports hooks and canUseTool — your function approving or rejecting every tool call in real time, in code.

The five principles of safe autonomy

Everything you've learned in the course distills into five principles. An agent that satisfies all five — you can truly release:

1. A feedback loop the agent runs itself

Autonomy without a way to verify success is guessing. Tests (Lesson 3), a browser (Lesson 7), compilation, lint — the agent needs a tool that tells it "you succeeded/failed" without a human. Phrase every task with a check criterion: "...and you're done only when all the tests are green".

2. Boundaries in code, not promises

Least-privilege permissions (allowedTools), blocking hooks (Lesson 6), readonly users (Lesson 7), deny rules and an isolated environment (Lessons 9–10). What's forbidden — make it impossible, not just "not recommended".

3. Quantitative brakes

maxTurns per run, cost monitoring from the returned JSON, and an external timeout. An agent stuck in a loop should stop by itself — not when you notice the bill.

4. External memory and slice-based work

Long tasks break into stages, each ending in a commit and a state-file update (PROGRESS.md — Lesson 4). An interrupted run resumes from the file, not from zero. Git is the backbone: every stage is reversible.

5. A human at the decision points

"Fully" autonomous doesn't mean "without humans" — it means the human moves from the inner loop to the checkpoints: the agent works alone for hours, but the deliverable is a PR you approve, and alerts (Notification hooks, send_alert) summon you when something unusual happens. You manage; you don't chaperone.

✅ The final test Before releasing an agent to run alone, ask: "what's the worst that could happen in this run?" If the answer is "a messy git branch I'll delete" — go. If the answer includes a real database, money or customers — principle 2 is missing. Go back and strengthen boundaries.

Exercises

Exercise 11.1 Your first agent in code

Run the TODO agent from the example (in whichever language suits you) on a real project. Then change the task to something of yours: generating a docs report, finding dead code, checking translation consistency. Follow the steps it chooses in the output.

If something gets stuck

Make sure the ANTHROPIC_API_KEY environment variable is set, and that allowedTools includes what the task truly requires (writing a report = needs Write). A "tool not allowed" error in the output is a precise hint at what's missing.

Exercise 11.2 A custom tool + judgment

Build a "project health checker" agent with one custom tool: report_status(status, details) that writes to a JSON file (or sends a real message — Telegram/Slack if you like). The task: "run tests and lint; report ok if all is well, and failed with details if not". Run it once on a healthy project and once on a broken one.

What you're testing here

That the agent uses your tool correctly: once with ok, once with failed + real failure details. If it reports ok on a broken project — sharpen the prompt ("actually run and read the output; don't assume"). Welcome to agent engineering.

Exercise 11.3 Capstone: the nightly agent

Put it all together: build an agent that runs on a schedule (cron or scheduled GitHub Actions) once a day on one of your repos, performing a maintenance task of your choice end to end — on a separate branch, with tests as the feedback loop, maxTurns, a state file, and a PR as the deliverable. Let it run three nights and review the results.

Recommended frame

Take nightly-deps.sh from Lesson 10 as the skeleton and swap the task: dead-code cleanup, improving test coverage ("add one test to the least-covered file"), or docs updates. Walk the five principles as a checklist before the first run. After three nights you'll know exactly what to strengthen — and that's precisely the skill of an agent engineer.
