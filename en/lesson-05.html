Custom commands and Skills

Any request you've caught yourself typing for the third time deserves to become a one-word command. In this lesson we'll build our own slash commands, then level up to Skills: knowledge packages Claude pulls in by itself at the right moment.

What you'll learn

  • Creating personal slash commands with parameters
  • The difference between a command (you invoke) and a Skill (the model invokes)
  • Building a complete Skill with helper files
  • Organizing and sharing with your team

Custom slash commands

A custom command is simply a Markdown file in the project's .claude/commands/ folder. The file name is the command name, and the content is the prompt that gets sent when you call it. Let's create one:

.claude/commands/check.mdRun a full quality check on the current changes:
1. Run the tests and the lint
2. Go over the diff and look for: bugs, duplicated code, unclear names
3. Verify there are no secrets (keys, passwords) in the code
4. Summarize findings in a table: severity, file, issue, suggested fix
Do not fix anything at this stage - only report.

That's it. From now on, in any conversation: /check — and the whole process runs.

Parameters with $ARGUMENTS

The string $ARGUMENTS in the file is replaced by whatever you type after the command name:

.claude/commands/fix-issue.mdRead issue number $ARGUMENTS using gh issue view.
Understand the problem, find the relevant code, fix it, add a test
that proves the fix, and show me a summary before committing.

Usage: /fix-issue 123. That's how a whole process — from reading the ticket to a proving test — becomes one command.

✅ Personal global commands Commands placed in ~/.claude/commands/ are available in all your projects. Commands in the project's .claude/commands/ go into git and are shared with the whole team — a team process library.

Skills — knowledge that loads itself

A slash command you invoke manually. A Skill is knowledge Claude invokes by itself when it recognizes the task fits. Every Skill is a folder with a SKILL.md file that starts with a metadata header:

.claude/skills/hebrew-ui/SKILL.md---
name: hebrew-ui
description: Rules for building Hebrew UIs with correct RTL. Use every
  time UI components with Hebrew text are created or edited.
---

# Building Hebrew UI

## Required rules
- On the root element: dir="rtl" and lang="he"
- Use margin-inline-start, not margin-left
  (same for all side properties: padding-inline, inset-inline, text-align: start)
- Numbers and code stay LTR: wrap with dir="ltr"
- "Forward/back" arrow icons flip in RTL - check direction

## Checks before finishing
1. No horizontal scrolling on the page
2. Punctuation at the end of Hebrew sentences renders correctly
3. Phone/email fields are LTR-aligned inside an RTL form

How does it work? At the start of a conversation Claude sees only each Skill's name and description. When a Hebrew-UI task arrives — it loads the full file on its own. That's why the description is everything: it must clearly state when to use the Skill.

A Skill with companion files

A Skill can also hold scripts, templates and helper files next to its SKILL.md:

.claude/skills/deploy-checklist/
├── SKILL.md          ← the instructions + when to trigger
├── checklist.md      ← the detailed checklist
└── verify.sh         ← a script the Skill says to run

In SKILL.md you write, say: "before a deploy run verify.sh and walk through checklist.md item by item". That's how you package a whole process — knowledge, automation and control — into one bundle the model knows how to activate.

💡 When a command, and when a Skill? Command — when you want control: "do X now" (/check, /fix-issue).
Skill — when you want knowledge applied automatically whenever it's relevant, without remembering to ask (RTL rules, API standards, deploy procedures).

Exercises

Exercise 5.1 Your first command

Think of a request you've already typed to Claude more than once, and turn it into a command in .claude/commands/. No idea? Create /explain — a command that explains a file: takes a path as $ARGUMENTS and returns a structured explanation: role, dependencies, weak points.

Sample solution 
.claude/commands/explain.mdRead the file $ARGUMENTS and explain:
1. Its role in one sentence
2. Its public API (main functions/classes)
3. What it depends on and what depends on it
4. Its most dangerous weak point
Keep it short and clear.
Exercise 5.2 A Skill that loads itself

Create a Skill named commit-style that defines a commit-message style (e.g.: a type: summary template, body explaining "why" not "what"). The description must make it load whenever a commit is created. Test: open a new conversation, make a change, ask for a commit — and check the style is enforced without you mentioning it.

Key point

If the Skill doesn't load — the problem is almost always the description. Phrase it as an answer to "when to use?": Use when creating git commits or writing commit messages. A too-generic description ("style rules") gives the model no reason to pull it in.

Exercise 5.3 A team library

Build a full "project kit": at least two commands (/check, /new-feature) and one Skill, and commit everything to git tidily. Bonus: ask Claude itself to build the commands — describe your process and it will write the files.

Why it's worth the effort

When .claude/ lives in the repo, every teammate (and every autonomous agent that will run on the repo in the future!) gets exactly the same processes. This infrastructure will serve you directly in Lessons 10–11.

Lesson summary

  • A custom command = a Markdown file in .claude/commands/, with $ARGUMENTS for parameters
  • A Skill = a folder with SKILL.md that Claude loads by itself based on the description
  • Commands: you invoke; Skills: the model invokes — each has its role
  • Everything goes into git, shared with the team and future agents
