Building an agent squad — principles, patterns and infrastructure

In Lesson 8 you met subagents — helpers one agent activates. Now we level up: an agent squad — a group of agents with defined roles, divided work and a shared deliverable. Like the difference between one talented employee and a whole department working for you.

What you'll learn

  • When one agent stops being enough — and when a squad is a mistake
  • The anatomy of a squad: roles, an orchestrator, shared memory and deliverable contracts
  • Three organizational patterns: pipeline, orchestrator–workers, parallel
  • Building it for real: in Claude Code and in the Agent SDK

Why a squad at all?

A single agent, however strong, has three structural limits:

  • One context window. A truly large task (research + planning + execution + testing + docs) bloats the context until quality drops. You met this in Lesson 4.
  • One hat at a time. Whoever wrote the code struggles to critique it objectively — true for humans, true for agents. A critic with separate instructions and a clean context finds problems the author misses.
  • Serial execution. Five independent tasks with one agent run one after another. Five agents finish them in a fifth of the time.
⚠️ But don't get carried away A squad costs more (tokens), is harder to maintain, and harder to debug. The rule: always start with one agent, and split into a squad only when you actually hit one of the three limits above. A squad is a solution to a problem — not decoration.

Anatomy of an agent squad

Every successful squad, in any field, is built from the same four components:

ComponentWhat it isHow to implement
OrchestratorWhoever breaks the goal into tasks, delegates and mergesClaude Code's main conversation, or an SDK script
SpecialistsAn agent per role: its own instructions, tools, permissionsFiles in .claude/agents/ (Lesson 8)
Shared memoryWhere the squad exchanges information and deliverablesFiles in the repo: SPEC.md, PROGRESS.md, an artifacts/ folder
Deliverable contractA precise definition of what each role receives and returnsAn "input/output" section in each agent's system prompt
💡 The most important principle: deliverable contracts Agent squads almost always fail at the same point — agent A returns a vague deliverable, and agent B doesn't know what to do with it. The solution: every agent finishes with a defined deliverable — "a PLAN.md with a numbered step list", "a findings report in a table with a severity per row". A defined deliverable = a clean handoff.

Three organizational patterns

1. Pipeline

Agents work one after another, each receiving its predecessor's deliverable: planner → builder → checker → documenter. Simple, predictable, easy to debug — when something breaks, it's clear at which station.

planner ──► builder ──► checker ──► documenter
 SPEC.md     code       report      README

Fits when work has a natural, fixed order and every stage depends on the previous one.

2. Orchestrator–Workers

An orchestrating agent holds the big picture, breaks down the task, and delegates each part to a specialist — as needed, not necessarily in fixed order. The orchestrator decides in real time: "does the researcher's finding require another check? I'll send the checker again."

              ┌──► researcher
 orchestrator ┼──► builder
 (decides)    └──► critic
       ▲______________│ (deliverables come back to it)

Fits when the task requires judgment about "what now" — not a fixed script.

3. Parallel–Merge

Split a task into independent parts, each agent works on one simultaneously, and a merge stage at the end. The clean way to do it in code: git worktrees — a separate working copy per agent, so they don't step on each other:

macOS / Linux# a separate working copy per agent, each on its own branch
git worktree add ../shop-payments feature/payments
git worktree add ../shop-search  feature/search

# terminal 1:
cd ../shop-payments && claude
# terminal 2:
cd ../shop-search && claude
Windows (PowerShell)git worktree add ..\shop-payments feature/payments
git worktree add ..\shop-search feature/search

# a terminal window per agent:
cd ..\shop-payments; claude
cd ..\shop-search; claude

Fits when parts are truly independent. The merge is where you pay the price — plan it in advance.

PatternWhen to choose itWeak point
PipelineA process with a clear, fixed orderSlow — everything is serial
Orchestrator–workersDynamic judgment about work order is neededThe orchestrator is a bottleneck and single point of failure
ParallelIndependent parts + a tight scheduleConflicts at the merge stage

Building it, way 1: everything inside Claude Code

The squad is defined as a set of files in .claude/agents/ (exactly like Lesson 8), and the main conversation serves as the orchestrator. The work script is packaged as a custom command — and the whole squad is launched with one word:

.claude/commands/build-feature.mdYou are a squad orchestrator. Build the feature: $ARGUMENTS
The working process, step by step:
1. Send planner to write SPEC.md with a detailed plan
2. Show me the plan and stop for approval
3. After approval - send coder to implement per the SPEC
4. Send test-writer to cover the new code with tests
5. Send code-reviewer for review; a critical finding goes back to coder
6. Summarize: what was built, what was tested, what remains open

Note step 2: a stop for human approval at the decision point — principle 5 from Lesson 11, now at squad level.

Building it, way 2: a squad in code with the Agent SDK

In the SDK you define the team members inside the options, and the model delegates to them exactly like subagents:

squad.tsimport { query } from "@anthropic-ai/claude-agent-sdk";

const result = query({
  prompt: "build a complete 'Contact' page: planning, implementation, tests and review",
  options: {
    agents: {
      planner: {
        description: "Planner. Use first for any new feature.",
        prompt: "Write a short, numbered implementation plan to SPEC.md. Do not write code.",
        tools: ["Read", "Grep", "Glob", "Write"],
      },
      coder: {
        description: "Implements according to an existing SPEC.md.",
        prompt: "Implement the SPEC.md steps one by one. Update PROGRESS.md after each step.",
      },
      reviewer: {
        description: "Code reviewer. Use after every implementation.",
        prompt: "Review the diff. Return a findings table with severity. Do not edit files.",
        tools: ["Read", "Grep", "Bash"],
      },
    },
    maxTurns: 60,
  },
});

for await (const message of result) {
  if (message.type === "result") console.log(message.result);
}

Exactly the same principles: a role, a deliverable contract (SPEC.md, PROGRESS.md, a findings table), and permissions per need — the reviewer doesn't get Edit.

Rules of thumb for a healthy squad

  • 3–5 roles are usually enough. A squad of ten agents is almost always a sign the problem was decomposed wrong.
  • One role = one responsibility. If an agent's description doesn't fit in a sentence, the role is too broad.
  • At least one critic. A squad with no review role (reviewer, checker, editor) is an assembly line of fast mistakes.
  • Everything through shared memory. A deliverable not written to a file — didn't happen. That's what enables stopping, resuming tomorrow, and debugging.

Exercises

Exercise 12.1 Your first pipeline

Create a minimal three-agent squad in your project: planner, coder, reviewer (you can build on the Lesson 8 agents). Write the /build-feature command from the example and run it on a small real feature. Follow the handoffs between agents.

What to check

The three handoff points: is SPEC.md created and detailed? Does the code actually follow the SPEC? Is the review report graded and pointing at files? If a handoff "leaked" (an agent ignored its predecessor's deliverable) — sharpen the receiving agent's contract: "first read SPEC.md and act only on it".

Exercise 12.2 Two agents in parallel

Pick two independent tasks in your project (say: improving page A and improving page B). Create two worktrees, run Claude in both in parallel, and merge the two branches at the end. Record: how much time did you save, and what did the merge cost you?

Key takeaway

If the merge went smoothly — the tasks were truly independent, and that's the pattern's real profit. If there were conflicts — you learned something more important: the boundary between the tasks ran through the wrong place. A good split follows the project's natural seams (different files/folders), not across them.

Exercise 12.3 The squad engineer

Take the squad from exercise 12.1 and break it on purpose: have the planner write a vague one-line plan ("build it well"). Run the chain and watch the error roll down the pipeline. Then fix — add a structure requirement to the planner (numbered steps, affected files, success criterion) and run again.

Why this exercise matters

In an agent squad, output quality is set by the weakest link — and it's almost always the handoff quality, not the agent quality. Comparing the two runs teaches more than any theory: a good plan at the start of the chain is worth more than a genius agent at its end.

Lesson summary

  • A squad = defined roles + an orchestrator + shared memory + deliverable contracts
  • Three patterns: pipeline (fixed order), orchestrator–workers (judgment), parallel (speed)
  • Start with one agent; split only on a real limit
  • A deliverable not written to a file — didn't happen; at least one critic per squad
